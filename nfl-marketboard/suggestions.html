In full, with options

S-01 · Pick one canonical NFL workspace and freeze the rest awaiting decision effort: large / medium / small
Problem
Sixteen NFL directories hold 387 pages built by different sessions on different days. They disagree with each other, and there is no way for a reader to tell which number is current. Every new session adds another.

Options

a. Consolidate into one namespace, archive the other fifteen
For: One answer per question; the site becomes usable; future sessions have one place to update.
Against: A large one-off integration job; risks losing a peer session's detail unless each page is migrated deliberately.
b. Keep all sixteen, but publish an index that says which is authoritative for what
For: Cheap; no content is lost.
Against: Does not fix the underlying disagreement; the reader still has to cross-check sixteen sources.
c. Freeze everything except one, and let new work land only there
For: Stops the sprawl growing; no migration cost.
Against: Leaves the existing contradictions in place.
Recommendation
Option (a) if you intend to keep using this repo; option (c) if you only want a stopgap. Option (b) alone is not enough.

S-02 · Triage the 534 rows with no source link awaiting decision effort: medium
Problem
The brief requires a source link on every row. 534 published rows do not have one. Some are proposals and legitimately have no external source; some state facts and should be sourced.

Options

a. Split every row into DATA or PROPOSAL and display the class
For: Makes the distinction explicit; proposals stop looking unsourced and data rows without a source become obvious.
Against: Needs a pass over each namespace.
b. Attach a source to every row, including proposals
For: Literal compliance.
Against: Forces a link onto rows where no link is meaningful, which is its own kind of noise.
c. Leave as is
For: No work.
Against: The verification rule stays unmet.
Recommendation
Option (a). It satisfies the rule honestly instead of cosmetically.

S-03 · Fill the replacement-depth column awaiting decision effort: medium (b) / small (a)
Problem
The brief asks whether a replacement is a 2nd, 3rd or 4th string player. The NFL publishes no depth chart, so the column is blank on every row and the requirement is unmet.

Options

a. Licence a depth-chart feed
For: Directly answers the question; cheapest in engineering time.
Against: Costs money; the provider becomes a dependency.
b. Derive depth from official gamebooks: count a replacement's prior starts this season
For: Fully official, free, and it produces an ordinal that actually means something: a replacement with zero prior starts is deeper on the chart than one with eight.
Against: One gamebook fetch per game per week — about 14 a week, or 270 a season. Needs automation.
c. Track only the fact of replacement, not its depth
For: Almost free; works today from the official injury report.
Against: Explicitly does not meet the brief, which asks for depth.
Recommendation
Option (b) if you want it free and official; option (a) if you want it fast. Option (c) is what is published now, and it is labelled as such.
Source
https://www.nfl.com/teams/new-england-patriots/depth-chart
S-04 · Snapshot the injury report on a schedule, not once awaiting decision effort: medium
Problem
One read per week cannot show when a designation changed, and designations change right up to kickoff. A single read also cannot be audited later.

Options

a. Store a dated snapshot on every read and graph the changes
For: Turns a static table into a timeline; makes "when did we know" answerable, which matters for any claim about timing an edge.
Against: Needs a scheduler and more storage.
b. Keep one read per week but record the exact read time
For: Minimal change; removes the ambiguity about freshness.
Against: Still no change history.
Recommendation
Option (a). Knowing when a designation changed is the whole point of tracking injuries.
Source
https://www.nfl.com/injuries/
S-05 · Fix the model before adding more data awaiting decision effort: large
Problem
The current model is measurably worse than the market: 0.569 points worse on the spread and 0.755 worse on the total. Collecting more games will make the measurement more precise, not make the model better.

Options

a. Add the features the model is missing: QB availability, replacement depth, rest, travel, and weather
For: These are the obvious gaps and two of them (QB availability, replacement depth) are already partly sourced here.
Against: Each feature needs its own official source and its own leakage control.
b. Replace the hand-built model with a fitted one on the same walk-forward harness
For: The harness already exists and enforces the time boundary; swapping the estimator is contained.
Against: Risks overfitting at n=137; still needs the sample floor before any claim.
c. Stop originating and buy a benchmark model instead
For: Removes the whole modelling problem.
Against: Then you are no longer originating your own lines, which was the point.
Recommendation
Option (a) first, then (b) once QB availability and depth are real columns rather than blanks.
Source
https://www.nfl.com/schedules/2026/by-week/week-1-10
S-06 · Get opening prices, or stop promising them awaiting decision effort: medium
Problem
Zero of 900 price rows have an opening number. Any metric that needs line movement — closing-line value, steam, open-to-close drift — is impossible until that changes.

Options

a. Licence a feed that captures the opening post
For: Unlocks line-movement metrics, which are the most robust evidence of skill available in this domain.
Against: Cost; and the historical backlog is still empty, so the metrics start from the licence date.
b. Backfill 2021, where the archive does hold both ends
For: Free and available today: the archive has Westgate opening lines and closing lines for the 2021 season, 272 games. That is enough to measure how far lines actually move.
Against: It is one season, from one book, five years ago.
c. Publish the column blank and revisit
For: Honest; no cost.
Against: Line movement stays unmeasurable, which caps how convincingly skill can ever be demonstrated.
Recommendation
Both (a) and (b): (b) gives you a movement prior this week, (a) gives you the real thing going forward.
Source
https://api.github.com/repos/nflverse/nfldata/contents/data
S-07 · Lower the 300-bet floor, or accept that nothing qualifies all season awaiting decision effort: medium
Problem
The pre-registered floor of 300 graded bets cannot be met this season: a 17-week NFL season produces at most about 272 games, and a filtered strategy bets far fewer than that. As written, no single-season strategy can ever qualify.

Options

a. Keep 300 and let qualification span multiple seasons
For: Statistically defensible; 300 is a reasonable floor for a hit-rate claim.
Against: Nothing can be awarded for roughly two years.
b. Add a provisional tier at n>=100 with a stricter p-value and a smaller reward
For: Gives the competition something to actually compete for this season without weakening the standard.
Against: Adds complexity; a provisional tier can be mistaken for a real one.
c. Score on out-of-sample prediction error instead of bet count
For: Uses every game rather than only the bets, so 137 results carry real weight; independent of staking entirely.
Against: Needs a new scoring definition and its own calibration.
Recommendation
Option (c) alongside (a). Prediction error is the better signal measure anyway, and it solves the sample problem without lowering any standard.

S-09 · Automate the weekly loop end to end awaiting decision effort: medium
Problem
Every number here was produced by a session that had to be asked. Scores, lines, injuries and grades should refresh themselves after each game without anyone prompting.

Options

a. A scheduled job: fetch official scores and the injury report, re-originate, re-grade, rebuild, push
For: The store stops going stale, which is currently its main weakness.
Against: Needs a runner and a secret for the push; the sandbox forbids long running processes, so this has to be GitHub Actions.
b. Keep it manual but document the exact command sequence
For: No infrastructure.
Against: Depends on someone remembering; gaps appear between runs.
Recommendation
Option (a). The repository already has GitHub Actions workflows for other namespaces, so the pattern exists.

S-10 · Write down what would change your mind awaiting decision effort: small
Problem
Eight strategies are being scored against six gates, but nobody has recorded in advance what result would cause you to abandon a strategy rather than keep explaining it.

Options

a. Pre-register an abandonment rule per strategy, dated and frozen before the next grading window
For: Removes the temptation to reinterpret a bad run as bad luck; this is the single cheapest anti-self-deception measure available.
Against: Takes an hour of writing.
b. Rely on the existing demotion gates
For: Already implemented.
Against: Gates act on results; they do not stop a human from re-framing the story around the results.
Recommendation
Option (a). It costs almost nothing and it is the difference between a research programme and a narrative.
