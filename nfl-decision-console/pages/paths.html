Decision paths

pick ONE path (paths differ on provenance and money, not on quality of code), then work its steps in order. A step may not start until its gate is cleared by its number. Nothing here is implemented by this namespace.

PATH-A — Official-only, price-free (no licence, no third-party numbers)

Publish model probabilities, availability indices and a skill-only leaderboard computed from league pages and from game books used as internal labels. No residual column, no CLV, no ROI, no paid rewards.

First step
Stand up the collector (CD-04 A) so availability becomes a dated series.
Gate that blocks it
Two or more dated captures per game week exist for 4 consecutive weeks.
Number that clears it
≥ 8 captures in a 4-week window, each with a hash, 0 missing required fields, drift alarm silent
Then, in order
  1. CD-03 A terms note → game-book label table for every fixture reachable
  2. CD-06 unit + gate definition → corpus page rebuilt from the standings identity
  3. CD-07 join → designation play rate with Wilson intervals and n
  4. CD-10/CD-14 skill division of the leaderboard, provisional flag until the window closes
It forbids
any 'market' word in a title; any correlation value computed from a non-official number; any payout
Cost
engineering only
Earliest leaderboard
a provisional skill division as soon as 148 fixtures are graded — i.e. today's corpus already exceeds a 100-fixture floor if the owner lowers the gate
Risk
the site can never answer 'is our line better than the market's', which is the question the origination programme exists to answer

standings read · live report

PATH-B — Official + licensed prices (the full programme)

Everything in PATH-A plus the price-snapshot store, fair/market/difference columns, residual published on a schedule, CLV escrow, two-stage leaderboard and rewards.

First step
Answer CD-02 with option A and name the vendor; store its terms in git with a hash.
Gate that blocks it
A licence exists and the vendor's history is downloadable at the granularity the snapshot store needs (open + close per market per game).
Number that clears it
≥ 1 season of closing lines downloadable before the first residual is published, and the ingest must reproduce the archive's own row count within 0 variance
Then, in order
  1. snapshot store with opening/closing numbers per market
  2. residual column appears on the origination page
  3. two-stage leaderboard: proper-score qualification then prospective CLV escrow
  4. rewards denominated in the escrow, never in the backtest
It forbids
paying on any window shorter than the registered prospective window; mixing vendor and scraped prices in one column
Cost
money + a collector + a terms review
Earliest leaderboard
the season after the archive starts, because CLV must be prospective
Risk
a dependency that can be killed by a budget line; every downstream claim inherits the vendor's provenance

price-source probes, both 404

PATH-C — Official + third-party archive, labelled on every row (no money)

PATH-A, plus research-grade residuals computed from a third-party price archive that is visibly not official, kept out of the public tables' titles.

First step
Answer CD-02 with option C and write the labelling rule into the publication contract: every row carrying a third-party number carries the label in the same row.
Gate that blocks it
The verifier enforces the label: a price-bearing row without a provenance label fails the build.
Number that clears it
100 % of rows with a non-official number carry a provenance field; a CI test that fails on 0 rows missing it
Then, in order
  1. same sequence as PATH-A, with residuals added as an internal grade only
  2. promote a residual to the public site only if the owner later relaxes the rule
It forbids
the word 'market' in a public title; a reward paid on third-party numbers; silence about provenance
Cost
labelling discipline only
Earliest leaderboard
as PATH-A, plus an internal residual track
Risk
a reader cannot tell which numbers the league published and which it did not — the label is the only defence, so the enforcement has to be a build failure, not a note

this namespace's own verifier, which is the enforcement mechanism proposed
